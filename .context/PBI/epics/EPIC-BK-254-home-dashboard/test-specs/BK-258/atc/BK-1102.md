# ATC Spec: BK-1102 - Open-bugs read rejects a workspace id that is not a UUID

> Ticket: BK-1102 (BK-258 TC10, P2, risk beyond AC)
> Component: OpenBugsApi (`tests/components/api/OpenBugsApi.ts`, existing)
> Type: API - Negative (input validation)
> Parent Story: BK-258

## 1. Test Case Summary

| Name | Objective | Precondition | Acceptance Criteria |
|------|-----------|--------------|---------------------|
| `expectBadRequestForMalformedWorkspaceId` | The workspace open-bugs read answers HTTP 400 `bad_request` when the path id is not a UUID, and the refusal leaks no counts | The default PAT held by the `{ api }` fixture satisfies `atc:read` (the handler authenticates before validating the id); no workspace id, seed data or DB access is needed | Risk beyond AC (input validation): a plain word, an ungrouped numeric string, an id 35 characters long and an id 37 characters long all answer 400 with only the error envelope |

## 2. ATC Contract

```typescript
/**
 * ATC: The open-bugs read rejects a workspace id that fails the route's UUID
 * regex with 400 `bad_request`, and the refusal carries only the error
 * envelope.
 *
 * Fixed assertions:
 *  - response status is 400
 *  - top-level body keys are exactly ['error'] (non-disclosure: neither
 *    open_count nor by_severity may leak, and any added top-level key fails)
 *  - body.error.code is 'bad_request'
 *  - body.error.message matches /workspace id must be a uuid/i
 *
 * The credential is not a parameter: it is whatever the `api` fixture set on
 * the component (the default login PAT), because the handler authenticates
 * before it validates the id.
 *
 * Assertion order matters: the key-set check runs before the property reads,
 * so a non-JSON or empty body fails as a clean assertion instead of a
 * TypeError on `body.error`.
 *
 * @param malformedWorkspaceId - a path id that fails the route UUID regex
 */
@atc('BK-1102')
async expectBadRequestForMalformedWorkspaceId(
  malformedWorkspaceId: string,
): Promise<[APIResponse, ErrorEnvelope]>
```

One positional parameter (the framework limit is two); the return is the
standard GET 2-tuple `[APIResponse, TBody]`. The ATC issues the GET and asserts
the complete outcome; it calls no other ATC and needs no helper.

### Why 400 is not part of `AccessExpectation`

BK-1101's `AccessExpectation` models an authorization decision for the
credential currently set on the component (401 / 403 / 200). BK-1102 holds a
valid credential and varies the input, so a 400 is not an access decision.
Adding it to `AccessExpectation` would make the union mean two different
things, force `expectAccessDecision` to learn a branch unrelated to the
credential, and invite a future reader to route input validation through the
authorization ATC. `AccessExpectation` and `expectAccessDecision` stay
unchanged, and the new ATC does not call `expectAccessDecision`.

## 4. Assertions Split

## 5. Code Template

ATC implementation (add to `OpenBugsApi` after BK-1101; `ErrorEnvelope` is
already imported by the component):

```typescript
@atc('BK-1102')
async expectBadRequestForMalformedWorkspaceId(
  malformedWorkspaceId: string,
): Promise<[APIResponse, ErrorEnvelope]> {
  const [response, body] = await this.apiGET<ErrorEnvelope>(
    `/v1/workspaces/${malformedWorkspaceId}/open-bugs`,
  );

  expect(response.status()).toBe(400);
  expect(Object.keys(body)).toEqual(['error']);
  expect(body.error.code).toBe('bad_request');
  expect(body.error.message).toMatch(/workspace id must be a uuid/i);

  return [response, body];
}
```

Test file (`tests/integration/home/rejectMalformedWorkspaceId.test.ts`,
fixture `{ api }`):

```typescript
/**
 * KATA Architecture - BK-258 Open-bugs API input-validation integration test
 *
 * TC10 (BK-1102): the workspace open-bugs read rejects a path id that is not a
 * UUID with 400 `bad_request` and leaks no aggregate. EP on the invalid
 * formats plus BVA at the UUID length boundary (35 / 37). One Playwright test
 * per row so every row gets its own fresh `api` request context and the `api`
 * fixture's default PAT is the only credential involved.
 *
 * Project: integration (depends on api-setup, no browser cookies)
 */

import { test } from '@TestFixture';

interface MalformedIdRow {
  label: string
  id: string
}

// EP: the invalid-format partitions (wrong characters / missing grouping).
const PLAIN_WORD: MalformedIdRow = { label: 'a plain word', id: 'not-a-uuid' };
const UNGROUPED_NUMERIC_STRING: MalformedIdRow = { label: 'an ungrouped numeric string', id: '1234567890' };

// BVA: the canonical UUID is exactly 36 characters; one short and one long.
const UUID_ONE_SHORT: MalformedIdRow = { label: 'an id one character short of a UUID (35)', id: '3f2504e0-4f89-11d3-9a0c-0305e82c330' };
const UUID_ONE_LONG: MalformedIdRow = { label: 'an id one character longer than a UUID (37)', id: '3f2504e0-4f89-11d3-9a0c-0305e82c3301a' };

const ROWS: ReadonlyArray<MalformedIdRow> = [PLAIN_WORD, UNGROUPED_NUMERIC_STRING, UUID_ONE_SHORT, UUID_ONE_LONG];

test.describe('BK-258: Open-bugs API input validation', { tag: ['@regression'] }, () => {
  for (const row of ROWS) {
    test(`BK-1102: should respond 400 when the open-bugs read is called with ${row.label} as the workspace id`, async ({ api }) => {
      await api.openBugs.expectBadRequestForMalformedWorkspaceId(row.id);
    });
  }
});
```

## 6. Technique-derivation check

| AC | Technique fired | ATCs produced |
|----|-----------------|---------------|
| Risk beyond AC: malformed path id on the open-bugs read | EP on the path id (valid UUID vs invalid formats) + BVA on the UUID length (35 / 36 / 37) | 1 parameterized ATC, 4 data rows |

**Equivalence Partitioning detail:**

| Input | Expected output | Same ATC? |
|-------|-----------------|-----------|
| Canonical UUID, 36 characters | 200 with counts | Not repeated: BK-1100 owns the accepted partition. It is listed only to delimit the partition |
| Plain word (`not-a-uuid`) | 400 `bad_request`, envelope only | Yes: row 1 |
| Ungrouped numeric string (`1234567890`) | 400 `bad_request`, envelope only | Yes: row 2 (same outcome shape as row 1, distinct invalid-format reason, kept as its own row per the TC's Examples) |
| Id 35 characters long | 400 `bad_request`, envelope only | Yes: row 3 (boundary) |
| Id 37 characters long | 400 `bad_request`, envelope only | Yes: row 4 (boundary) |

**Boundary Value Analysis detail** (the route constrains the id to exactly 36
characters in the canonical 8-4-4-4-12 grouping):

| Field + range | Boundary rows |
|---------------|---------------|
| Path id length, valid = 36 (fixed) | 35 -> 400 (row 3); 36 -> 200 (BK-1100, not repeated); 37 -> 400 (row 4) |

The 35- and 37-character ids are the valid UUID
`3f2504e0-4f89-11d3-9a0c-0305e82c3301` with its last character removed and with
one character appended, so only the length boundary changes and the other four
groups stay well formed. Both fail the anchored regex (11 and 13 hex digits in
the last group instead of 12).

**BVA-D**: N/A. Nothing is rounded or truncated; the id is rejected or
accepted as a whole.

**Notes that keep the partitions honest:**

- The regex is case-insensitive (`/i`), so an uppercase canonical UUID is a
  VALID input, not an invalid partition. It is therefore not a row here.
- `1234567890` fails because of the missing 8-4-4-4-12 grouping, not because
  digits are rejected: `0-9`, `a-f` and `A-F` are all accepted by the class. A
  hyphenated all-digit string such as
  `12345678-1234-1234-1234-123456789012` would PASS this format-only regex and
  is deliberately not used.
- All four ids are URL-safe, so the request reaches the route handler and the
  400 comes from `isUuid`, not from Next.js routing.

**Reduction axes:**

| Parameterized ATC | Reduction applied | Rows after reduction |
|-------------------|-------------------|----------------------|
| `expectBadRequestForMalformedWorkspaceId` | none: one factor (the id string); no Decision Table or Pairwise combination to reduce | 4 |
