# ATC Spec: BK-1377 - An unrecognised expansion is refused, named, and leaks no payload

> Ticket: BK-1377 (BK-595 TC10, P0, AC-02 / 2.3, ROI 10.00)
> Component: AtcsApi (`tests/components/api/AtcsApi.ts`, new in this Work Package)
> Type: API - Negative (input validation)
> Parent Story: BK-595 (`TMS-ATC API | Read a single ATC by id`)

## 1. Test Case Summary

| Name | Objective | Precondition | Acceptance Criteria |
|------|-----------|--------------|---------------------|
| `expectInvalidExpandRejected` | An `expand` token outside the four published names answers 400 `bad_request`, the message names the offending token, `details.reason` is `expand_invalid`, and no ATC payload is returned | A valid ATC id so validation reaches the expand parser (the id is checked first); credential holding `atc:read` | AC-02 / 2.3: 400, `error.code = 'bad_request'`, message contains the invalid token, `details.reason = 'expand_invalid'`, `details.value` = the token, top-level keys exactly `['error']` |

## 2. ATC Contract

```typescript
/**
 * ATC: An unrecognised `expand` value is rejected with 400 `bad_request`
 * (`details.reason = 'expand_invalid'`), naming the offending token and
 * returning no partial ATC payload.
 *
 * Fixed assertions:
 *  - status 400
 *  - top-level body keys are exactly ['error']
 *  - body.error.code is 'bad_request'
 *  - body.error.message contains the invalid token
 *  - body.error.details matches { reason: 'expand_invalid', value: <token> }
 *
 * The id must be a valid UUID: the handler validates the id BEFORE it parses
 * expand, so a malformed id would answer 400 for the wrong reason.
 */
@atc('BK-1377')
async expectInvalidExpandRejected(
  args: { atcId: string, expand: string, invalidToken: string },
): Promise<[APIResponse, ErrorEnvelope]>
```

One positional parameter that carries three values (the framework limit is two, so the object shape is used). The credential is not a parameter.

## 3A. API Details

| Aspect | Value |
|--------|-------|
| Endpoint | `GET /api/v1/atcs/{id}?expand=<mixed>` |
| Types | `ErrorEnvelope` (`@schemas/auth.types`), `APIResponse` (`@playwright/test`) |
| Auth | Bearer `atc:read` — resolved by the wrapper before the handler body runs |
| Order inside the handler | `extractAtcId` → `isUuid` (400 on failure) → `parseAtcExpand` (400 on failure) → RPC → expansions |
| Parser contract | `parseAtcExpand` returns `{ ok: false, invalid }` on the first token outside `ATC_EXPANSIONS`; it never drops an unknown token silently |
| Error mapping | `ApiError('bad_request', ...)` maps to HTTP 400 in `lib/api/error-envelope.ts`; the body is `{ error: { code, message, request_id, details } }` |
| Message | `Unrecognised expand value '<token>'. Allowed: steps, assertions, acceptance_criteria, used_in.` |
| Source of truth | `app/api/v1/atcs/[id]/route.ts` (GET), `lib/atcs/expand.ts` (backend repo, read-only) |

## 4. Assertions Split

### Fixed (inside ATC)

- `expect(response.status()).toBe(400)`
- `expect(Object.keys(body)).toEqual(['error'])` — the non-disclosure assertion: no `atc` key and no partial payload
- `expect(body.error.code).toBe('bad_request')`
- `expect(body.error.message).toContain(args.invalidToken)`
- `expect(body.error.details).toMatchObject({ reason: 'expand_invalid', value: args.invalidToken })`

### Test-level (in test file)

- Which token rides alongside the valid ones (`steps,bogus`); nothing else is repeated.

## 5. Code Template

```typescript
@atc('BK-1377')
async expectInvalidExpandRejected(
  args: { atcId: string, expand: string, invalidToken: string },
): Promise<[APIResponse, ErrorEnvelope]> {
  const [response, body] = await this.apiGET<ErrorEnvelope>(
    `/v1/atcs/${args.atcId}?expand=${encodeURIComponent(args.expand)}`,
  );

  expect(response.status()).toBe(400);
  expect(Object.keys(body)).toEqual(['error']);
  expect(body.error.code).toBe('bad_request');
  expect(body.error.message).toContain(args.invalidToken);
  expect(body.error.details).toMatchObject({
    reason: 'expand_invalid',
    value: args.invalidToken,
  });

  return [response, body];
}
```

## 6. Technique-derivation check

| AC | Technique fired | ATCs produced |
|----|-----------------|---------------|
| AC-02 / 2.3 (unknown expansion refused) | EP on the token (published vs unrecognised) | 1 ATC, 1 row |

**Equivalence Partitioning detail:**

| Input | Expected output | Same ATC? |
|-------|-----------------|-----------|
| `steps,bogus` | 400 naming `bogus`, envelope only | Yes — row 1 |
| `STEPS` / ` steps ` | 200, normalised to `steps` | Not repeated: normalisation is BK-1376 (parser rules, pending automation) |
| `bogus` alone | 400 naming `bogus` | Same partition as row 1; one row is enough because the message assertion pins the token, not its position |
| Malformed id plus invalid expand | 400 naming the **id** | Not repeated: precedence is BK-1382 (deferred) |

**Boundary Value Analysis**: N/A — the parser classifies tokens, it does not range over a value. **BVA-D**: N/A.

**Why mixed rather than bare**: a bare `expand=bogus` would also pass if the parser rejected every request that carries `expand`. Mixing one valid token with the invalid one proves the request was refused for the token named in the message.
