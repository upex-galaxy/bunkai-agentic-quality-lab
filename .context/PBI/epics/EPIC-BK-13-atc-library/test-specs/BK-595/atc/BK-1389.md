# ATC Spec: BK-1389 - Repeated reads leave the ATC unchanged

> Ticket: BK-1389 (BK-595 TC22, AC-06 / 6.1, Level: API)
> Component: `AtcsApi` (existing, extended in this Work Package)
> Type: API - Positive (no side effects)
> Parent Story: BK-595 (`TMS-ATC API | Read a single ATC by id`)

## 1. Test Case Summary

| Name | Objective | Precondition | Acceptance Criteria |
|------|-----------|--------------|---------------------|
| `expectRepeatedReadsLeaveAtcUnchanged` | Reading the same ATC repeatedly - lean, expanded, lean, expanded again - never advances `version` and never moves `updated_at`, and the expanded payload keeps returning the same steps | An accessible ATC in the caller's workspace and a credential holding `atc:read`; the ATC needs at least one step so the expanded rows are meaningful | AC-06 / 6.1: `version` identical across the four reads, `updated_at` identical across the four reads, `id` stable, steps content identical between the two expanded reads |

## 2. ATC Contract

```typescript
/**
 * ATC: Four reads of one ATC (lean, fully expanded, lean, fully expanded again)
 * leave the resource untouched.
 *
 * Fixed assertions:
 *  - all four responses are 200
 *  - body.atc.version is identical across the four reads
 *  - body.atc.updated_at is identical across the four reads
 *  - body.atc.id equals the requested id on every read
 *  - the steps array of the first expanded read deep-equals the second
 */
@atc('BK-1389')
async expectRepeatedReadsLeaveAtcUnchanged(
  atcId: string,
): Promise<[APIResponse, AtcGetResponse]>
```

One positional parameter; the credential is whatever the fixture set on the component. The ATC issues four reads internally (they are the ACTION under test, not calls to other ATCs) and returns the last read's tuple.

## 3A. API Details

| Aspect | Value |
|--------|-------|
| Endpoint | `GET /api/v1/atcs/{id}` (lean) and `GET /api/v1/atcs/{id}?expand=steps,assertions,acceptance_criteria,used_in` |
| Types | `AtcGetResponse`, `AtcResource` (`@schemas/atc.types`) |
| Version source | `bunkai_get_atc` row `version`; only `bunkai_update_atc` (PATCH) bumps it |
| Timestamp source | `updated_at` on the `atcs` row; written only by the update RPC |
| Route guarantee | The GET handler performs no write: it calls `getAtc`, optionally one `acceptance_criteria` select and the `atcUsage` RPC (both read-only) |
| Cache interaction | Reads are `private, no-store`, so no intermediary can serve a stale copy that would make the comparison vacuous |
| Source of truth | `app/api/v1/atcs/[id]/route.ts` (GET), `lib/supabase/rpc.ts` `getAtc` / `atcUsage` (backend repo, read-only) |

## 4. Assertions Split

### Fixed (inside ATC)

- `expect(response.status()).toBe(200)` on each of the four reads
- `expect(expanded.atc.version).toBe(lean.atc.version)`, the same for the second lean read and for the second expanded read
- `expect(expanded.atc.updated_at).toBe(lean.atc.updated_at)`, the same for the second lean read and for the second expanded read
- `expect(body.atc.id).toBe(atcId)` on each read
- `expect(expandedAgain.atc.steps).toEqual(expanded.atc.steps)`

### Test-level (in test file)

- The seed ATC id. Nothing else: the whole business meaning lives in the ATC.

## 5. Code Template

```typescript
@atc('BK-1389')
async expectRepeatedReadsLeaveAtcUnchanged(atcId: string): Promise<[APIResponse, AtcGetResponse]> {
  const [firstResponse, first] = await this.apiGET<AtcGetResponse>(`/v1/atcs/${atcId}`);
  expect(firstResponse.status()).toBe(200);

  const [expandedResponse, expanded] = await this.apiGET<AtcGetResponse>(
    `/v1/atcs/${atcId}?expand=steps,assertions,acceptance_criteria,used_in`,
  );
  expect(expandedResponse.status()).toBe(200);

  const [secondResponse, second] = await this.apiGET<AtcGetResponse>(`/v1/atcs/${atcId}`);
  expect(secondResponse.status()).toBe(200);

  expect(expanded.atc.version).toBe(first.atc.version);
  expect(second.atc.version).toBe(first.atc.version);
  expect(expanded.atc.updated_at).toBe(first.atc.updated_at);
  expect(second.atc.updated_at).toBe(first.atc.updated_at);
  expect(first.atc.id).toBe(atcId);
  expect(expanded.atc.id).toBe(atcId);
  expect(second.atc.id).toBe(atcId);

  // Second expanded read: content must not drift while `version` stands still.
  const [expandedAgainResponse, expandedAgain] = await this.apiGET<AtcGetResponse>(
    `/v1/atcs/${atcId}?expand=steps,assertions,acceptance_criteria,used_in`,
  );
  expect(expandedAgainResponse.status()).toBe(200);
  expect(expandedAgain.atc.version).toBe(first.atc.version);
  expect(expandedAgain.atc.updated_at).toBe(first.atc.updated_at);
  expect(expandedAgain.atc.steps).toEqual(expanded.atc.steps);

  return [expandedAgainResponse, expandedAgain];
}
```

## 6. Technique-derivation check

| AC | Technique fired | ATCs produced |
|----|-----------------|---------------|
| AC-06 / 6.1 (reads never write) | State-transition check: the observable state before and after the read sequence must be identical | 1 ATC, 1 row |

**Equivalence Partitioning detail:**

| Read shape | Expected output | Same ATC? |
|------------|-----------------|-----------|
| Lean read | `version`, `updated_at` unchanged | Yes - rows 1 and 3 of the sequence |
| Fully expanded read (four joins, including the `used_in` RPC) | `version`, `updated_at` unchanged | Yes - row 2; the expanded path is the only one that runs extra queries, so it is the one that could accidentally write |
| PATCH on the same id | `version` +1 | Not this TC: the edit route is BK-18 / BK-21, and BK-1390 (TC24) owns "leave PATCH unchanged" |

**Boundary Value Analysis**: N/A - no ranged input. The meaningful boundary is "1 read vs repeated reads", covered by the three-read sequence.

**Implementation note**: the sequence is four requests - lean, expanded, lean, expanded again. The second expanded read is what makes the step-content comparison meaningful (content drift with an unchanged `updated_at` would be a silent corruption the AC exists to catch). Dropping it would still cover the AC's version/timestamp clause, so if the reviewer prefers three requests the ATC loses only the content-stability assertion. DECIDED: keep four.

**Reduction axes**: none - single factor (repetition of a read), one partition.
